How popular programming languages perform with MySQL

Methodology and test environment

Every post in this series uses the same test setup. This page describes it once, so the posts can focus on results. It covers what we measured, how we kept the comparison fair, the hardware and server configuration, and the limits of the test.

The question

We did not run compute benchmarks such as tight loops or simulations. Most application code spends its time talking to a database, so we asked a more practical question: how much does a language and its MySQL driver cost under real concurrency? In practice you never benchmark a language on its own. You benchmark a language together with the driver its ecosystem actually uses.

Thirteen languages took part. Each one uses its most common MySQL driver with default settings. The concurrency column matters for several results in the series. It shows how each implementation runs its workers.

Python's mysqlclient driver does not support server-side prepared statements. It formats query parameters on the client instead. The Lua implementation calls the libmysqlclient text protocol directly. We kept both choices because they reflect how these languages are commonly used. Each affected post points out where this matters.

The four workloads

All languages run the same four workloads. Every worker opens its own connection and does a fixed amount of work, so total work grows with the number of workers.

WorkloadWhat each worker doesReported as
1. Integer insertInserts 100,000 random integers with a prepared 10-row multi-row INSERT, executed 10,000 times. Autocommit is on, so each statement commits on its own.rows/s
2. Integer fetch and sumRuns one prepared SELECT val FROM bench_int LIMIT 100000, fetches every row and sums the values in application code with a 64-bit accumulator.rows/s
3. Blob insert and MD5Generates 20 pseudo-random 1 MiB blobs, computes each blob's MD5 in application code and inserts each blob with its own commit.blobs/s
4. Blob read and MD5Reads back its own 20 blobs by primary key with a prepared SELECT and computes each blob's MD5 in application code.blobs/s

The tables are deliberately minimal. bench_int has a single INT column and no index. bench_blob has a BIGINT primary key and a LONGBLOB column.

How a test run works

  • Concurrency sweep. Each workload runs at 4, 8, 16, 32, 64, 128, 256 and 512 concurrent workers.
  • Fixed work, not fixed time. Every language does identical work, and elapsed time is the result.
  • Ordering. At each worker count, a write workload runs first and its read workload follows. The insert tables are truncated before each write workload. The data is already in the buffer pool when it is read, and there is no separate warm-up phase.
  • Timing. Workers connect and prepare their statements first, then wait at a start barrier. The clock starts when the barrier is released and stops when the last worker finishes. Connection setup is outside the timed window.
  • Same random data. Every implementation uses the same 31-bit linear congruential generator, seeded per worker, and must reproduce a reference sequence before its results count.
  • No connection pooling. Each worker owns one connection for the whole run.
  • TLS disabled everywhere. Some drivers enable TLS by default when it is available. Disabling it everywhere keeps encryption cost out of the comparison.
  • Three runs. The full sweep ran three times for every language. The charts show the average.

How CPU cost is measured

Client CPU is the user plus system time of the whole benchmark process, measured with /usr/bin/time. Server CPU is the change in the mysqld process's CPU counters across the same run, read from /proc. Measuring both lets us tell whether a language is slow because the database is saturated, because the client is burning its own CPU, or because the client is waiting on a lock while both sides sit idle.

Test environment

Each language ran on its own host against a Percona Server instance on the same machine. The client connects over TCP to 127.0.0.1, so there is no physical network in the path. All hosts are identical. Where two or three languages share a host, they ran one after another, never at the same time.

Server configuration

The server is tuned for raw throughput, not durability. The buffer pool is far larger than the data, so reads never touch disk. Commits do not wait for a disk flush, the doublewrite buffer is off and binary logging is disabled. This keeps the database out of the way as much as possible, so differences between clients show up clearly. Do not use these settings for production data.

Limits of this test

Every benchmark makes trade-offs. These are the ones worth knowing when you read the results.

  • Client and server share a machine. At high worker counts they compete for the same 80 logical CPUs. A client that uses a lot of CPU also slows down the server it talks to.
  • Some runs are short. The fastest languages finish workload 2 in well under a second. There is no warm-up phase, so just-in-time compilers in Java, C#, Node.js and LuaJIT warm up inside the timed window.
  • Run-to-run variation. For a typical data point the three runs differ by about 7% from slowest to fastest. Short read runs at low worker counts vary the most. We draw conclusions only from differences much larger than that.
  • Client CPU includes startup. Process start, runtime initialisation and connection setup count toward client CPU, though not toward elapsed time. This mainly affects the shortest runs.
  • Runtime defaults. We did not tune garbage collectors, thread pools or similar runtime settings. Some languages improve a lot with tuning. We report defaults because that is what most applications run with.
  • One concurrency model per language. Python and Ruby use threads, which is where their interpreter locks show up. Production deployments often run multiple processes instead. That is a valid way to scale, but it is a different test.

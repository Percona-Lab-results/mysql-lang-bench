How popular programming languages perform with MySQL · Part 1

PHP and Lua keep pace with C on MySQL. Python and Ruby don't.

We gave thirteen languages the same simple job: read rows from MySQL and add them up, with up to 512 workers at once. Four scripting languages split into two very different groups. The reason is not interpreter speed. It is how each language runs work in parallel.

This series asks a practical question. How much does a language and its MySQL driver cost under real concurrency? Most code doesn't run tight compute loops. It talks to a database, so that is what we measured. The methodology page has the full test setup, which is shared by every post in the series.

The test

Each worker opens its own connection, runs one prepared SELECT that returns 100,000 integers, fetches every row and sums the values in application code. The rows are already in the server's memory, so the database does very little work. Almost all the cost is in the client: receiving rows, turning them into values the language understands and adding them up. We ran this with 4 to 512 concurrent workers and measured rows per second.

PHP and Lua: within 10% of C

With 128 workers, Lua reaches 93% of C's throughput and PHP reaches 90%. Both keep climbing all the way to 512 workers, just like the native languages. For this workload, choosing PHP or Lua over C costs you almost nothing.

Two things make this possible:

  • A thin path to C. PHP's mysqli runs on mysqlnd, a driver written in C. Our Lua implementation calls libmysqlclient directly through LuaJIT's foreign function interface, with almost no conversion in between. Very little interpreted code runs for each row.
  • Separate processes. Neither PHP nor Lua has shared-memory threads, so each worker is a forked process. Processes share no interpreter state, so there is no lock for them to fight over. Forking is expensive, but here it happens once per worker, before the clock starts.

Python and Ruby: more threads, no more speed

Python's throughput barely moves. It does 1.5 million rows per second with 4 workers and 2.0 million with 512. Adding 128 times more workers gives about 30% more throughput. At 128 workers, PHP and Lua are about 11 times faster.

Both Python and Ruby run their workers as real operating system threads. Both drivers also release the interpreter's global lock while they wait on the network, so the waiting does overlap. But every step that touches a language object needs that lock: turning a row into a Python or Ruby integer and adding it to the total. Only one thread can do that at a time, so the threads queue up behind each other.

The CPU numbers show this clearly. Python keeps about 1.4 CPU cores busy whether it runs 4 threads or 512. That is one thread doing useful work at a time, plus some driver work outside the lock. The machine has 80 logical CPUs, and Python leaves almost all of them idle.

Ruby is further behind still. It peaks at about 158,000 rows per second with 32 workers and then slowly declines. Unlike Python, Ruby does not sit idle. With 128 workers it keeps about 10 cores busy for nearly 90 seconds to read rows that PHP finishes in under a second. Ruby also starts lower: with only 4 workers it is already more than 30 times behind C, so the cost per row is high even before lock contention sets in. Our Ruby implementation streams the result set row by row, while the PHP, Lua and Python implementations load it into memory first. That difference probably accounts for part of Ruby's per-row cost, and we will measure it separately.

JavaScript and TypeScript: in between

Node.js lands in the middle, at about 54% of C with 128 workers. Its workers run in worker_threads, and each one has its own JavaScript engine instance, so there is no shared lock. The cost comes from the driver instead. mysql2 parses the MySQL wire protocol in JavaScript, so every row passes through JavaScript code. Throughput levels off around 13 million rows per second at 64 workers and above. TypeScript compiles to JavaScript and uses the same driver. It tracks JavaScript closely, sometimes slightly ahead and sometimes up to about 15% behind, which is within the run-to-run variation of these short runs.

The driver isn't the explanation

It is tempting to credit the driver for these results, but C, Swift, Lua and Python all use the same C library, libmysqlclient. C and Lua end up near the top of the chart, and Python near the bottom. With the same C library underneath, the gap has to come from what happens around it: how many workers can run language code at the same time.

What this means for your application

  • "Scripting language" doesn't predict database performance. PHP and Lua sit with the native languages. Python and Ruby sit far below. The concurrency model decides the outcome, not whether the language is interpreted.
  • For Python and Ruby, scale with processes, not threads. Running several processes with a few threads each, as most production deployments do, sidesteps the global lock. Each process then has its own lock to contend with. Python's new free-threaded build, which removes the global lock, is another option worth testing.
  • Watch idle cores, not just busy ones. A Python service that seems light on CPU may be stuck waiting for its own lock. Low CPU use does not mean the service has room to grow.

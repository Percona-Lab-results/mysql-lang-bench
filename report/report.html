Findings

  • Server CPU per transaction is nearly identical for every language (~1.6 ms at low concurrency, ~2.1–2.6 ms under contention) — expected, since all clients execute the same statements, and a useful validity check for the whole comparison.
  • C, C++, Swift, Rust and PHP saturate the server (~29 k tps at 128–256 workers) while spending only 0.3–0.9 ms of client CPU per transaction — the server is always their bottleneck.
  • Go’s collapse at 32–128 workers is client-side runtime burn: its client CPU jumps from ~0.6 ms to ~4 ms per transaction (GC/scheduler defaults on an 80-core client; GOMAXPROCS=16 GOGC=800 recovers ~3×). At 512 workers the Go client consumes more total CPU than mysqld.
  • JavaScript and TypeScript are the costliest clients (~2.8 ms/txn at 4 workers, ~12.4 ms at 512) — mysql2’s pure-JS protocol parsing. TypeScript tracks JavaScript within a few percent everywhere: compilation adds no runtime cost.
  • C# scales to 64 workers then degrades under the default workstation GC (DOTNET_gcServer=1 measured 2.4× faster at 256 workers).
  • Python stays at ~1 k tps regardless of workers (GIL), and its text protocol (no server-side prepares) costs the server ~18% extra CPU per transaction.
Methodology: per-worker PRNG with identical streams across languages; warmup excluded from the timed window via a start barrier; retries on deadlock/lock-wait/duplicate-key with full redraw. CPU window covers the full run (connect + warmup + timed + teardown), slightly wider than the throughput window but identical in shape for every language. Client CPU = user+sys of the whole benchmark process tree; server CPU = mysqld utime+stime delta. Sources: results/<host>/*.json, results/summary.csv.
